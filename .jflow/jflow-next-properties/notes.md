# jflow-next-properties notes

- Spec session ran on google (`gemini-4-neon`, high) instead of the configured anthropic seat (`claude-opus-5-5`, medium).

## Build
- One test, `test_next_properties.py`, 164 lines. Each run builds a real git repo with random receipts, reruns with and without code changes, `Checks allowed:` and `Yes:` lines, Maybes, `[edge]`/`[use]`/untagged and carried defects, and Accepted lines in five variants (right, wrong sha, committed before the receipt, prose that only mentions the item, none). The oracle works out the expected step from what the generator built, not from `jflow.py`'s parsing. It compares only the step or the kind of human stop (approach, cap, stuck, edge, gate, done), not the card text.
- Default seed is fixed at 1, so the default run is deterministic and the mutants below fail every time. Run i uses seed SEED+i, so a printed seed reruns alone with `JFLOW_PROP_RUNS=1`.
- `jflow.py` is unchanged: 2,800 generated runs across seeds 1–600, 1000–1400, 2000–2400 and 3000–3400 all agree with `next` at HEAD. One disagreement turned up along the way (seed 1551): the oracle followed carried lineage only one hop, while `next` follows it back to the check the defect started in. That was an oracle bug, and `next` matches SKILL.md ("carried verdicts included").
- Mutants I ran, each one string replaced in a copy of `jflow.py` (each failed): the 2f8aaa8 `- <?none\b` Maybe filter (seed 13); 38b1e04 prose acceptance (seed 6); f6fb039 with the commit-order condition dropped (seed 6); `counted = len(receipts)` (17); `yes()` matching any `Yes:` (10); `allowed[0]` (43); `elif stuck and not edge` (33); `or defects:` sending `[edge]`-only to fix (33); `accepted_late` returning False (4).
- Default run: about 4.6 s for 50 runs. 80 runs take about 7.9 s. unittest reports one test however many runs it covers.

## Fix 1 (check-1)
- Defects 1–4 had one cause: random runs rarely reached the decisive state for a rule. Four of the checker's mutants passed the default 50 seeds, and several of mine were caught by only one seed. The fix gives each seed a story, `seed % 7`: before the build, all proved, `[edge]`-only, stuck, waiting, fix at the cap, and late acceptance at the cap. Everything else in the run is still random, and the seed alone still reproduces it. Receipts draw from named shapes. A receipt with only BLOCKED or WAITING rows is mostly rerun without a code change. Acceptances are none, all right, or all present with a mix of right and wrong variants. The fix and late stories write a higher `Checks allowed:` line followed by a lower one.
- Coverage, measured with a scratch harness that runs every mutant on each seed: across the default seeds 1–50, every mutant from `drive.py` and every one of mine fails at least 2 seeds (skip-approach 2, no-late 3, f6fb039 4, count-blocked-or-waiting 4, the rest more). Seeds 51–100 and 101–150 catch each mutant at least once. All `drive.py` modes now pass.
- Defect 5: the test fails when `JFLOW_PROP_RUNS` is less than 1. Defect 6: fixture git commands run with `GIT_DEFAULT_HASH=sha1`; the default run passes with `GIT_DEFAULT_HASH=sha256` set.
- At HEAD, `next` still agrees with the oracle on 1,200 runs from seeds 1, 1000, 2000 and 3000 (300 each). `jflow.py` is unchanged.
- Cost: the default run takes about 6.4 s, up from 4.6 s, because the stories make more receipts. The file is 177 lines, a little over the spec's "about 150 to 170", to pay for the story table.

## Fix 2 (check-2)
- Defect 1: the generator carried only defects, so lineage for rows went untested. Now any open row or defect in a later check can be "carried from check-j". The oracle follows each item back through every source check that has it, the way `next` does. An eighth story, `carried`, has at least two checks and carries most of the newest check's items. Mixed acceptance mode now makes exactly one line wrong, so that line decides the outcome. For a carried item the wrong line is "here": it names the newest check's sha. Otherwise it is a wrong sha, committed before the receipt (double weight), or prose that only mentions the item.
- Defect 2: the test runs with every `GIT_*` variable removed (and `GIT_DEFAULT_HASH=sha1`), so an exported `GIT_DIR` reaches neither the fixtures nor `next`. With `GIT_DIR` set to another repo, that repo still has only its own commit afterwards.
- A bug of mine, found by the 300-run sweep from seed 1000: the carried story crashed when the newest check carried nothing. It now falls back to any item.
- Coverage across the default seeds 1–50: every mutant fails at least 2 seeds. The checker's carried-row copy fails 7 (seed 14 first). Seeds 51–150 catch every mutant except count-blocked-or-waiting, which misses all of 101–150. The default seeds catch it twice. At HEAD, 1,200 runs from seeds 1, 1000, 2000 and 3000 agree with `next`, and `jflow.py` is unchanged.
- `drive.py carried-row` and `drive.py foreign-git-dir` now fail on their own asserts. Each asserts the defect's behavior: the buggy copy passing, and the caller's repo gaining commits.
- Cost: the file is 184 lines, more than the spec's "about 150 to 170". The extra lines go to the eight stories and the per-item lineage. The default run takes about 5.7 s.
